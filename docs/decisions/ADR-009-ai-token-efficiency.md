# ADR-009: AIトークン消費の計測と削減（キャッシュ永続化・出力上限・暴走防止）

- 日付: 2026-07-26 ／ 状態: 採択
- 関連: ADR-002（データ層フォールバック）、ADR-004（研究室ページ充実）、ADR-005（カードデッキ）、docs/03 付録A、NFR-EXT-01、AC-05

## 文脈

「システム全体のトークン消費効率を最高効率にする」という依頼を受け、実測から始めた。

**計測が存在しなかった。** `server/ai.ts` はproviderのusageを一切読んでおらず、どの機能が何トークン使うか誰も知らない状態だった。まず `server/ai-telemetry.ts` を追加し、実データを取得した（本番相当のAPIキー・2026-07-26）。

| 機能 | input | output | うち推論 | 所要 |
|---|---|---|---|---|
| question-craft step1（3コール合計） | 6,521 | 9,651 | 791 | 77秒 |
| ├ RQ候補12件生成 | 2,164 | 6,797 | 267 | 52秒 |
| ├ 公開文リライト（12件全部） | 3,662 | 1,342 | 493 | 11秒 |
| └ brief | 695 | 1,512 | 31 | 14秒 |
| smart-search（自然文検索1回） | 456 | 94 | 38 | 2.2秒 |
| enrich:guide（研究室1件） | 451 | 427 | 17 | 5.4秒 |

`cachedInputTokens` は全コールで **0**（プロンプトキャッシュは一度も効いていない）。

## 判明した最大の問題：キャッシュが本番で機能していなかった

`enrich.ts` と `lab-cards.ts` はAI生成物を `process.cwd()/data/runtime/*.json` へ `fs.writeFileSync` していた。しかし
①VercelのNodeランタイムは `/var/task` が読み取り専用のため書き込みは常に例外（catchで握りつぶされ、ログにしか出ない）
②`data/runtime` はgit未追跡（0ファイル）なのでデプロイ時点でも空

つまり本番では両キャッシュが**インスタンス内メモリのみ**で、コールドスタートごとに全消失していた。CLAUDE.mdとdocs/03が「7日TTL」「週次共有ウィンドウ240件でコスト上限」と記載していたコスト設計は、本番では成立していなかった。同じ読み取り専用FS問題は同日にClaim保存でも見つかっており（ADR-002追記）、これはその第2例である。

## 決定

### 1. AI生成物のL2キャッシュを永続化する（最重要）

既存の `mishiru_api_cache` テーブル（schema.sqlに定義済みだが未使用だった）を再利用する。新テーブルを増やさず、RLS有効・公開ポリシー無し＝service_roleのみという必要な性質をすでに満たしているため。`scope` と `version` は `cache_key` に埋める（`enrich:v4:lab-123`）。

- 実装: `server/ai-cache.ts`
- 構成: **L1=プロセス内メモリ（既存のまま）→ L2=Supabase（全インスタンス共有・永続）**
- 各呼び出し側のTTL/SWR判断は変更していない。この層は永続性だけを足す
- `/tmp` 層は**採らない**。Vercelでは `/tmp` とプロセスメモリは同寿命（同一インスタンス限り・コールドで両方消失）で、L1がある以上冗長なため
- 適用先: enrich（研究室ガイド）、lab-cards（カードデッキ）、smart-search（検索意図の解釈）

### 2. smart-searchに解釈キャッシュを新設する

自然文検索は**キャッシュが一切無く**、同じ語での再検索・リロード・共有リンク・`?ai=`付きURLへのアクセスがすべて課金対象だった。

保存するのは「検索意図の解釈（fields/areas/keywords）」だけで、研究室のスコアリングは**キャッシュしない**。前者はクエリだけで決まり研究室データが増えても変わらない（＝使い回せる）が、後者はCPUだけで安く、かつデータ更新を即反映すべきだから。**高い部分だけを保存する。**

キーはNFKC正規化＋trim＋空白圧縮＋小文字化。「AIで仕事はどう変わる？」「ＡＩで仕事はどう変わる?」「 ...　」を1件として扱う。TTL 30日。

### 3. 出力上限と推論の強さを実測値から設定する

6箇所の呼び出しが `maxOutputTokens` も `reasoningEffort` も指定しておらず、既定の**8000上限＋provider既定の推論**で動いていた。実測出力の3〜5倍を上限とし（切り詰めによる再生成のほうが高くつくため余裕を持たせる）、`reasoningEffort: "low"` を明示した。

smart-search 400 / enrich:guide 1500 / lab-cards 5000 / interest-analysis 4000 / report 6000 / qc:adjust-text 1200。

### 4. 暴走を止めるブレーカーを置く

`MISHIRU_AI_DAILY_CALL_LIMIT` で1日あたりのLLM呼び出し上限を設ける。超過時は `callAI` がnullを返し、各呼び出し側の決定的フォールバックへ落ちる＝**画面は壊れずコストだけ止まる**（AC-05の考え方）。厳密な分散カウンタではない（インスタンス毎に最大60秒の誤差）が、目的は「桁を止める」ことなので許容する。docs/03の「コスト上限」を初めて実体化する仕組み。

### 5. クローラにAI生成をさせない

sitemapが19,785件の研究室URLを公開しており、`/api/labs/:id/enrich` は無認証・無レート制限だった。クロール1周でAI生成が同数走りうる。

- `public/robots.txt` を新設し `/api/` をDisallow（研究室ページ本体はSEOのためクロール可のまま）
- 既知のクローラUAには**生成済みキャッシュだけを返す**（生成させない）二重防御

CAPTCHA・認証・有償WAFは過剰と判断し採らない。

### 6. RQ候補はAIが選んだ4類型だけ生成する（2026-07-26 ユーザー判断により実施）

12類型すべてをAI生成し、さらに12件すべてを公開文リライトへ渡していた。しかし画面の初期表示は推奨3〜4件で、残りは折り畳みの中。**モデル自身に「この素材に最も合う4類型」を選ばせ、その4件だけ生成・リライトする**方式へ変更した。残り8類型は既存の決定的テンプレート（`fallbackCandidates`）が`repairCandidates`で自動的に埋めるため、**「ほかの問い案を見る」の件数・並びは12件のまま変わらない**。

実測（同一入力・free_input）:

| | 変更前 | 変更後 |
|---|---|---|
| step1合計 | in 6,521 / out 9,651 | **in 5,052 / out 6,109** |
| ├ RQ候補 | out 6,797 | out 3,615 |
| └ 公開文リライト | in 3,662 / out 1,342 | in 2,059 / out 867 |

**合計31%減・出力37%減。** 副次的に品質も上がった。従来は`repairCandidates`が推奨枠を固定インデックス`[0,2,5,11]`で機械的に埋めていたが、いまはモデルが素材に応じて選ぶ。「会議で本音を言えない」という入力に対しR2分類/R3関係要因/R5プロセス/R6意味解釈が選ばれ、品質スコアは94〜97（テンプレートは82）。

注意点として実装時に踏んだ罠：`repairCandidates`は候補が見つからないとき`generated[index]`で位置的に拾うため、4件だけ返すとR4の内容がR2に化ける。生成が12件そろったときだけ位置対応を使うようガードした。

待ち時間は78秒でほぼ変わらない。3コールの逐次実行とコール毎のオーバーヘッドが支配的で、出力量が律速ではなかったため。短縮したい場合は逐次を並列化する別の手当てが要る。

### 7. その他

- **enrichのSWRはTTL切れのみに限定する（当初案を実装中に撤回）**：「版ズレも陳腐化として扱えばコストの崖を避けられる」と考えて一度実装したが、`CACHE_VERSION` を上げるのは「前の出力はもう正しくない」という宣言であり（v6の公開根拠ゲート導入がまさにそれ）、古い内容を配り続けると掲載してはいけない情報が生き残る。実際、受入テストのFR-ENRICH-02a/02b/03が版ズレ配信を検知して落ちた。**コストより正しさを優先**し、版ズレは同期再生成に戻した。TTL切れ（版は一致＝内容は正しいが古いだけ）のSWRはそのまま維持する
- **interest-analysisの素材を圧縮**：上限なしで `JSON.stringify(materials)` していたため、素材200件でプロンプトが7万字を超えていた。直近40件＋モデルが使わないメタ情報（id/URL/日時/検証状態）を落として1万字程度に収める
- **スタンピード防止**：同一キーの生成がプロセス内で並走しないよう `withSingleFlight` で束ねる
- **二重生成の除去**：`/api/discovery-cards` が `getDeckCards` の返り値を捨てて `buildCardsFor` を再実行していた

## 追記（2026-07-29）：機能別モデル割当と、モデル固定が外れていた事故

### きっかけ
OpenAIの値下げ（**Luna -80% / Terra -20%**、Solは値下げ対象外で「APIでより高速なオプション」のみ）。ユーザー指示「軽量な生成は全てLunaへ」。

### 調査で判明した事故：全機能がSol（最上位・値下げ対象外）で動いていた
2026-07-22に `LOCKED_AI_MODEL = "gpt-5.6-terra"` でTerraへ固定したが、**その後の公開ハードニングでモデル選択UIと `withAiModel` ミドルウェアが撤去され、固定を適用する呼び出し自体が消えていた**。`withAiModel` は定義だけが残り参照ゼロ。結果 `currentAiModel()` は `defaultAiModel()` へ落ち、その既定値が `gpt-5.6-sol` だったため、**全生成がSolで実行されていた**。

実測で確認（`x-mishiru-ai-model: gpt-5.6-terra` を付けても無視され `model=gpt-5.6-sol`）。ユーザーが指示した固定は約1週間、無効のままだった。

**教訓**: 「定数で固定した」だけでは守られない。固定は*適用点*（ミドルウェア）とセットで、かつ**実測ログのmodelフィールドで継続検証**しないと、無関係な改修で静かに外れる。ADR-009で計測を入れていたおかげで発見できた。

### 決定：envと固定定数をやめ、機能別ルーティングを唯一の決定点にする

`server/ai.ts` の `modelForFeature(feature)` が唯一の決定点。envの `AI_MODEL` は既定値の上書きにのみ使い、未設定・不正値なら `CORE_MODEL`（Terra）。Solへ落ちる経路（`modelForProvider` の既定値）は削除した。

| 割当 | 機能 | 根拠 |
|---|---|---|
| **Luna（軽量）** | `smart-search` | 出力57〜94tok。分類コード+キーワード抽出。辞書フォールバックあり |
| | `enrich:guide` | 出力427tok・定型JSON。**全研究室ページで最多件数**。テンプレフォールバックあり |
| | `lab-cards` | 8枚バッチの定型JSON。テンプレカードあり |
| | `qc:adjust-text` | 一段落の書き換え。失敗時は原文を返すので無害 |
| | `report` | 管理者向け・低頻度・テンプレフォールバックあり |
| **Terra（中核）** | `qc:rq-candidates` | 中核価値そのもの。唯一のmedium reasoning |
| | `qc:brief` | 焦点カードとして最初に読まれる。異質素材の統合判断 |
| | `qc:public-rq` | FR-QUESTION-05の平易さ要件。劣化するとテンプレに落ち機械的な文になり、**主画面の4枚に直接出る** |
| | `qc:literature` | 実在論文の要約。誤情報が致命 |
| | `interest-analysis` | 1日1回制限で頻度が低く、節約効果が薄い割にリスクだけ増える |

未知ラベルは安全側（Terra）へ倒す。providerフォールバック時も重みを保つ（軽量→`gemini-3.1-flash-lite`／中核→`gemini-3.5-flash`）。

### 実測（同一処理・Sol→Luna/Terra）

| 機能 | 変更前(Sol) | 変更後 | 備考 |
|---|---|---|---|
| smart-search | 459 in / 59 out | **Luna** 463 in / 65 out | 出力量ほぼ同じ |
| enrich:guide | 451 in / 427 out | **Luna** 451 in / 426 out | 出力量ほぼ同じ。推定表現・字数規定とも維持 |
| qc:brief | 695 in / 1,512-1,627 out・30秒 | **Terra** 672 in / 1,463 out・**14.7秒** | 所要が約半分 |
| デッキ生成(lab-cards) | 18〜20秒 | **1.5〜5.6秒** | 受入テストFR-CACHE-01の実測 |

品質は劣化していない。Luna生成の研究室ガイドは「〜のようです／〜と考えられます」の推定表現、中高生向けの平易さ、questions3件・methods3件・各字数規定をすべて満たした。

### 見送り
- `qc:public-rq` のLuna化：頻度は高いが、失敗時に落ちるテンプレ文が機械的で、しかも主画面の4枚に直接出る。日本語の平易化は劣化が目立ちやすいため据え置き。**下げるなら実測比較の上で**（品質ゲート `isPlainPublicQuestion` の弾き率を指標にできる）
- `interest-analysis` のLuna化：1日1回制限で件数が出ないため、リスクに見合わない

## 見送った判断（意図的）

- **qc:rq-candidates の reasoningEffort を medium→low に下げる**：アドバイザーは単発レバー最大と評価したが、**実測の reasoningShare は 3.9%（6,797トークン中267）** にすぎず、削減効果は限定的。一方でこのコールは最も難しい生成であり品質劣化リスクは実在する。実測を優先して見送る
- **プロンプトキャッシュ（provider側）の追求**：`cachedInputTokens=0` は故障ではなく構造的なもの。3プロンプトとも静的接頭辞がOpenAI自動キャッシュの下限（1024トークン）に届かず、低トラフィックでは共有窓にも乗らない。本命は上記のアプリ側キャッシュであり、費用対効果が低いため追わない

## 影響

- キャッシュがコールドスタートを跨いで効くようになり、docs/03 付録Aの「7日TTL」「週次240件」というコスト上限が本番で初めて実体を持つ
- `/api/admin/ai-usage` で機能別の実測（input/output/推論/キャッシュヒット率）を常時確認できる。Vercelログでは `tag=ai_usage` で追える
- Supabase未設定環境（ローカル開発）はL1のみで従来どおり動作する（AC-05）
