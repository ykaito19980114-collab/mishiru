# ADR-010: 問いをつくるジャーニーの再設計（段階表示・自動保存・課金束ね・使用量計測）

- 日付: 2026-07-28 ／ 状態: 採択
- 関連: FR-QUESTION-01〜06、SCR-11、ADR-007（Clear Board）、ADR-009（トークン効率）、AC-05
- 起点: ユーザー指示「生成のプロセス変更を経て、ユーザーが迷いなく生成するためのジャーニーを描きなおし、全面的に見直す。トークン効率と一石二鳥の設計を点検。使用トークン総量を常時表示」

## 文脈（実測に基づく現状の問題）

1. **78秒の無言の待ち**: step1は1つのブロッキングPOST（内部はbrief 15-25s→候補生成45s→リライト9sの逐次3コール）。UIはボタン内スピナーのみ。スケルトンも進捗も中間表示も無い（Questions.tsx:138）
2. **ステッパーが嘘**: .step-railのCSSは4カラム定義済みだが、JSXは単一spanしか描画せず、currentStepは2を飛ばす（Questions.tsx:65,141）
3. **価値ある生成物が全部折り畳み**: 素材統合の根拠・focus・domain_shifts（毎回~1,100字生成）・what_we_learn・方法・難しさが1〜2段の開閉の奥。4候補の比較に4回の手動展開が要る
4. **選択が不活性**: カード選択は色が変わるだけで、次のCTAは折り畳み8件の下
5. **ゴール前のフォームの壁**: 2分の生成後、保存モーダル（タイトル/サブタイトル/ステータス/表紙）を通すまで何も永続化されない。閉じたらサーバー生成物は消える
6. **ゲスト消費が見えない**: step1/step2で計2/5回消費するが残回数は画面に出ず、78秒待った後に登録モーダルに当たる
7. **step2の待ちは不要**: 骨子は決定的テンプレで即時生成できるのに、文献LLM1コールと同じPOSTに同梱され全体をブロックしている

## 決定

### J1. step1を2つのエンドポイントに分け、待ち時間を「先行成果物を読む時間」に変える

- `POST /api/question-craft/brief`（15-25秒）: 研究ブリーフのみ生成して返す
- `POST /api/question-craft/candidates`（~55秒）: briefを往復で受け取り、AI選抜4類型の候補生成＋平易化リライトまで行い、完全なStep1Responseを返す

UIはbrief到着時点で**焦点カード**（「あなたの関心をこう捉えました」= 採用した焦点・対象/現象/文脈・AI仮定は「推測」明示）を描画する。ユーザーがこれを読んでいる間に候補が届く。**リライト前の未検査テキストは表示しない**（FR-QUESTION-05の平易さ保証はリライト合流点にあるため。粗い版を出して9秒後に差し替える案は、読み始めた文章の差し替え害の方が大きいため不採用）。

進捗表現は**実段階のみ**: 各フェーズ1本の正直なコピー＋経過秒数（tabular-nums）。candidates内部の生成→リライト遷移はサーバー内で観測できないため、偽のタイマー切替で「段階風」を装うことは禁止する（SSEは複雑さに見合わず不採用）。

### J2. domain_shiftsを「別の見方」チップとして機能化（死蔵データの再利用）

焦点カードに最大6方向のチップを表示。クリックで `candidates` だけを `focusOverride` 付きで再実行する（briefは再利用）。従来のフル再実行よりbrief分のトークンを節約しつつ、毎回生成して捨てていた~1,100字が機能になる。生成中のチップは「生成が終わったら選べます」の理由付き非活性。

### J3. 候補カードは「常時表示＝選ぶための情報／開閉＝深掘り」に再配分（FR-QUESTION-06準拠）

- 常時: rq_title（主役・大きく）／public_rq／「この問いで分かること」1行（what_we_learn・生成済みだが死蔵だった）／平易な型ラベル（"R3"等の記号は出さず表示層の静的マップで変換）／方法・難しさのメタ1行
- 4枚が同型構造なので、比較テーブルを作らずとも走査で比較できる（同型メタ行方式）
- 開閉（details）: 専門向けRQ・構成要素・期待成果物・品質スコア等（現状維持）
- 選択＝ライム枠（ADR-007の選択色）。選択と同時に画面下部の固定action-barへ「この問いで研究プランをつくる」を出す（選択→操作の距離ゼロ）
- テンプレ由来の8件は「ほかの問い案（下書き・8件）」の開閉に維持

### J4. 保存モーダルを廃止し、問いを選んだ瞬間にプランが存在する

- `POST /api/question-craft/outline`: 決定的骨子（LLM無し・即時）＋fallback文献＋`literatureStatus:"pending"` でStep2Responseを組み、**サーバー側でプロジェクトを自動作成**してprojectIdを返す。タイトルはrq_titleを仮置き（プロジェクト画面でいつでも変更可）。表紙は既定プリセット
- クライアントは即 `/projects/:id` へ遷移し、到着トースト「研究プランを作成しました。タイトルはあとから変えられます」
- ProjectDetailは `literatureStatus:"pending"` を見て文献セクションを「先行研究を確認しています…」行にし、`POST /api/question-craft/literature {projectId}` で充填（15-30秒・唯一のLLM）。成功で`verified`、失敗時はfallback文献のまま`fallback`とし**「下書き（未確認の参考例）」ラベルを明示**（実装規約「未確認は未確認と表示」）。失敗行だけの再試行ボタンを置く
- 二重作成防止: outlineはsingle-flight＋actionId鍵のレスポンスキャッシュで冪等（並行二重POSTも再送も同じprojectIdを返す）。作成成功時にドラフトを消去するため、再訪時に古い選択が残って誤作成する経路も無い

### J5. ゲスト課金はactionIdで束ね、レスポンスキャッシュで再実行の穴も塞ぐ

- brief+candidatesは**同一actionId**を共有 → requireValueActionの既存冪等性により合計1消費（従来: step1で1消費と同等。「別の見方」再生成は新actionId＝新規1消費）
- outline（+自動作成）は1消費。single-flight＋actionId応答キャッシュの二重で並行二重POSTでも1プロジェクト
- **literatureは無課金・actionId束ねをしない**（実装時にJ4当初案から変更。プロジェクトへのactionId永続化が不要になる）。代わりに構造で有界化する: `literatureStatus`がpending/fallbackの時だけ実行可＋projectId single-flight＋aiRateLimit。**再試行ループがLLMを浪費しない根拠**: LLMコール（文献要約）はOpenAlexで実在文献が見つかった場合にのみ走り、その同じ呼び出しが`verified`へ遷移させてループを終端する。文献が見つからない限り再試行はOpenAlex照会（無料・レート制限内）だけでLLMに到達しない。つまり「無料LLMの無限実行」経路は存在しない
- **既存の穴への対処**: consumeは同一actionIdの再送を「無課金で通す」だけで再実行自体は止めないため、1消費で同じ生成を無限に走らせられた。本改修で `brief/candidates/outline` のレスポンスを actionId鍵でキャッシュ（TTL 24h・成功時のみ保存）し、再送はLLMを走らせず同一レスポンスを返す。悪用封じ・リロード復帰・再送安全の一石三鳥
- 残回数の可視化: 生成CTAの近くに「無料であと◯回」を常設（useAccountAccessの既存値。ログイン時は非表示）

### J6. 3駅レールを本物にする

`書く → 選ぶ → プラン` の3駅。既存.step-rail CSSを実際に使い、現在地を正しく反映。保存は駅ではない（J4で自動化されたため）。

### J7. AIトークン使用量の常時表示（運営者向け）

- 集計の永続化先は**専用テーブル `mishiru_ai_usage_daily`**（day主キー・in/out/reasoning/cached/calls/failures）。mishiru_api_cacheはTTL付きキャッシュ表でありパージで消えうるため使わない（アドバイザー指摘採用）。各AI呼び出し完了時に`mishiru_record_ai_usage` RPCで日本時間の日次行へ原子的に加算し、サーバーレス停止や複数インスタンス競合でも取りこぼさない。RLS有効・公開ポリシー無し・anon/authenticated権限無し。schema.sqlとmigrationを同梱（未適用環境ではメモリ内集計のみで劣化動作＝AC-05）
- ai-telemetryのrecordAiCallから60秒デバウンスで当日行へフラッシュ
- `GET /api/admin/ai-usage` に `today / thisMonth / cumulative`（計測開始2026-07-26以降）を追加
- **表示は管理画面のみ**: admin全タブ共通ヘッダーに「AIトークン 今日◯／今月◯／累計◯」を常設。一般ユーザーには出さない（研究初心者を萎縮させる・運営コスト情報のため。refcraft-webの「トークン消費あり」注記は本サービスの対象者には移植しない）

## 移行と互換

- 旧 `POST /api/question-craft/step1` `/step2` は当面併存（受入テスト・/api/projects/quick・regenerateが使用。デプロイ跨ぎの旧クライアント対策も兼ねる）。内部実装は新分割関数の合成に置き換え、挙動は不変
- localStorageドラフトは従来どおりstep1/選択/step2を保持（中断復帰の下地。briefのみ完了状態も保持対象に追加）

## 一石二鳥の棚卸し（本ADRでの採用分）

| 施策 | UX効果 | トークン/コスト効果 |
|---|---|---|
| brief先行表示 | 待ち時間が読む時間になる | 追加コストゼロ（分割のみ） |
| 別の見方チップ | 死蔵データが機能になる・再生成の入口が明確 | 再生成時にbrief分(~2,300tok)節約 |
| actionIdレスポンスキャッシュ | リロード復帰・再送安全 | 無限再生成の穴を封鎖・重複実行ゼロ |
| 骨子の即時化 | プラン到達が2分→数秒 | LLMコール数は不変（分割のみ） |
| 自動作成 | フォームの壁の消滅・生成物が消えない | 放棄による再生成（=再課金トークン）を削減 |
| 文献のプロジェクト内充填 | 失敗時にその行だけ再試行 | 失敗時の全再実行が不要になる |

## 見送った判断

- **SSE/ストリーミング**: candidates内部の段階を見せる唯一の正直な手段だが、Vercel Functions＋Express構成での複雑さに見合わない。将来、リライトを生成プロンプトへ内蔵して1コール化（9秒と1コール削減）する方が筋が良い
- **リライト前テキストの先出し→差し替え**: 読んでいる文章の差し替えは害の方が大きい
- **モバイル下部タブへの追加**: タブ構成はIA-02でdocs固定。導線はハンバーガー＋各ページからのリンクを維持
